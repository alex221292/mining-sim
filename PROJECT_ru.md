# Mining Sim — спецификация проекта

## Видение

Mining Sim — двумерная игра о добыче полезных ископаемых с видом сбоку, визуально вдохновлённая Terraria и механически — симуляциями падающего песка. Долгосрочная цель — подземный мир, в котором раскопки имеют физические последствия: песок обрушивается, вода затапливает туннели, разные породы ведут себя по-разному, а деревянные опоры помогают укреплять выработки.

**Проект разрабатывается постепенно и служит обучению.** Первым результатом должна быть не игра, а небольшая интерактивная песочница материалов, позволяющая изучить построение детерминированной тестируемой симуляции и заменяемого рендерера.

## Принципы проектирования

1. **Сначала симуляция.** Мир может развиваться без окна или GPU.
2. **Сначала CPU.** Java2D — временный рендерер; симуляция не должна зависеть от типов Java2D.
3. **Ориентация на данные там, где это полезно.** Хранить клетки в массивах примитивов, а не создавать объект для каждой клетки.
4. **Маленькие измеримые шаги.** Каждый этап должен давать запускаемый и тестируемый результат.
5. **Никаких преждевременных фреймворков.** Без Spring, контейнера внедрения зависимостей, универсальной ECS, системы плагинов и сложной шины событий.
6. **Явные компромиссы.** Сначала простые правильные правила, затем сложные приближения.
7. **Детерминированные тесты.** Симуляция должна принимать seed для любой случайности.

## Начальный технологический стек

- Java 25 (JDK 25)
- Gradle с Gradle Wrapper; использовать версию Gradle, совместимую с JDK 25
- Java2D / AWT / Swing для прототипа
- JUnit Jupiter для автоматических тестов
- Без стороннего физического движка
- Позднее, опционально: LWJGL + OpenGL для рендеринга

## Начальный объём: этап 1 — песочница падающего песка

Запускаемое настольное приложение со следующими возможностями:

- Окно с рисуемым миром, изначально **400 × 300 клеток**; масштабирование по размеру окна (например, 2 экранных пикселя на клетку).
- Мир на основе плоского массива примитивов с небольшим enum `Material` или таблицей ID.
- Материалы: `AIR`, `STONE`, `SAND`, `WATER`, `WOOD`.
- Рисование мышью с выбором материала кисти; правая кнопка стирает до воздуха.
- Песок падает вниз, а при препятствии — по диагонали.
- Вода падает вниз, а при препятствии течёт вбок.
- На этом этапе камень и дерево неподвижны.
- Симуляция с фиксированным шагом (цель — **60 тиков симуляции в секунду**) независимо от рендеринга.
- Управление паузой, продолжением, одиночным шагом и очисткой/сбросом.
- Базовый overlay: FPS, тики симуляции в секунду, количество активных клеток или другая полезная диагностика.
- Модульные тесты индексации мира, поведения материалов, границ и детерминированных обновлений.
- README с инструкциями по сборке и запуску.

### Критерии приёмки

1. `./gradlew test` выполняется успешно.
2. `./gradlew run` открывает песочницу в поддерживаемой графической среде.
3. Песок, нарисованный над воздухом, падает; вода течёт; камень и дерево неподвижны.
4. Рисование и симуляция у границ не вызывают доступа за пределы массива.
5. Пауза останавливает обновления симуляции; одиночный шаг продвигает ровно один тик.
6. Код симуляции не импортирует `java.awt.*`, `javax.swing.*` или классы OpenGL.
7. Рендерер можно заменить без переписывания правил обновления материалов.
8. Фиксированные начальный мир и seed дают воспроизводимые состояния симуляции.

### Не входит в этап 1

Персонаж, инструменты добычи, инвентарь, крафт, процедурный ландшафт, бесконечный мир, чанки, освещение, система сохранений, сеть, структурная устойчивость, физика на GPU, реалистичная гидродинамика и масштабная многопоточность. Это возможные будущие направления, а не требования первого этапа.

## Предлагаемая минимальная архитектура

Предлагаемые пакеты (можно изменить, если более простая структура понятнее):

```text
src/main/java/.../miningsim/
  Main.java                 # точка сборки приложения
  app/                      # окно, ввод, цикл приложения
  world/                    # World, Material
  simulation/               # Simulation, правила обновления
  render/                   # абстракция рендерера, реализация Java2D
src/test/java/.../miningsim/
```

### Модель мира

На этапе 1 используйте мир фиксированного размера:

```java
final class World {
    private final int width;
    private final int height;
    private final byte[] materials; // y * width + x
}
```

Явно определите безопасное поведение при доступе за границы. Не раскрывайте изменяемые внутренние массивы за пределами пакета симуляции. Добавляйте отдельные массивы свойств только при наличии обоснованной функциональности.

### Модель симуляции

- Предоставить независимый от интерфейса метод `step()`, продвигающий один фиксированный тик.
- Для материалов под действием гравитации предпочитать обход снизу вверх; не допускать случайного многократного перемещения клетки за тик.
- Чередовать направление горизонтального обхода или использовать детерминированный выбор с seed для уменьшения смещения в одну сторону.
- Чётко определить правила перемещения материалов и протестировать их по отдельности.
- Начать с дискретных игровых правил жидкости, **не** SPH/Навье — Стокса.
- Избегать выделений памяти для каждой клетки в горячем цикле.
- Отслеживать изменённые/активные области только после получения правильной реализации с полным обходом сетки и обоснования профилированием.

### Модель рендеринга

Рендерер отвечает за отображение состояния мира, но не за обновление физики. В реализации Java2D предпочтительно записывать цвета в повторно используемый буфер пикселей `BufferedImage` и масштабировать изображение вместо вызова `fillRect` для каждой клетки. Типы AWT/Swing должны оставаться в коде приложения и рендеринга.

Абстракция рендеринга должна быть небольшой. Будущая реализация OpenGL может загружать текстуру пикселей/ID и раскрашивать её шейдером. **Перенос рендеринга на GPU не переносит туда физику автоматически**; это отдельное значительно более масштабное изменение.

### Время и ввод

Использовать фиксированный шаг симуляции с аккумулятором и максимальным количеством догоняющих шагов за кадр. Согласовать обработку событий Swing/AWT и изменение симуляции, чтобы избежать гонок данных. Начальная реализация может быть однопоточной, кроме потока обработки событий AWT, если ввод безопасно передаётся в цикл симуляции.

## Дорожная карта

### M1 — интерактивная песочница материалов

Мир фиксированного размера, песок/вода/камень/дерево, Java2D, рисование, пауза/шаг, диагностика и тесты.

### M1.5 — укрепление симуляции и базовые замеры

Реализованы детерминированные тесты инвариантов, ограниченное окно измерения времени тика в overlay, детерминированный headless-бенчмарк и заметки об архитектуре и производительности. В описанном запуске на Ryzen 9 5900X / JDK 25 средняя длительность шага активного мира составила 1.079 мс (400×300), 4.413 мс (800×600) и 13.414 мс (1600×900). Это исследовательские измерения одного запуска без графики, а не гарантия времени кадра; методика, остальные сценарии и ограничения — в `docs/performance-baseline_ru.md`. Проверка нового overlay в графическом интерфейсе остаётся невыполненной.

### M1.6 — течение воды

Вода отдаёт приоритет перемещению вниз, по диагонали и затем ограниченному боковому движению; добавлены детерминированные тесты бассейна и сохранения материалов. За одно горизонтальное перемещение частица воды может пройти до восьми последовательных пустых клеток, по-прежнему не более одного перемещения за тик. Это локальная дискретная аппроксимация, а не модель давления или скорости. Сценарий бассейна и бенчмарк до/после описаны в `docs/water-flow_ru.md`; графическое поведение после изменения в этой среде не проверено.

### M2 — производительность и более разнообразные материалы

Реализованы профилирование с Java Flight Recorder, явные ID и категории материалов, гравий и локально связный грунт, тесты взаимодействия и бенчмарки на крупных мирах. По умолчанию используется FULL_SCAN; ACTIVE_REGIONS остаётся экспериментальным из-за накладных расходов на плотных мирах и различий порядка обновления. Правила и ограничения материалов: `docs/materials_ru.md`; замеры: `docs/m2-material-performance_ru.md`. Хранение чанками и глобальная структурная механика не вводились.

### M3 — мир из чанков и камера

Хранение чанками, камера/область просмотра, генерация мира, спящие/неактивные чанки, формат сохранения.

Реализованы камера M3.1 и ограниченное чанковое хранение 64×64 M3.2; генерация, потоковая подгрузка чанков и сохранения остаются будущей работой. Результаты бенчмарка полного обхода и существенные накладные расходы хранения в этой среде описаны в `docs/m3-chunk-performance_ru.md`.

M3.3 добавляет проверки переходов через границы и жизненного цикла активности, необязательный headless-бенчмарк распространения и диагностику; существующие физика и экспериментальное планирование активности не изменены. Ограничения и результаты — в `docs/m3-activity-propagation_ru.md`.

### M4 — добыча и структурная устойчивость

Игрок, инструменты раскопок, размещение опор, простые проверки устойчивости по компонентам связности, падение отделившихся масс или их превращение в обломки. Позже — приближённые нагрузки, прочность пород и разрушение опор. **Не заявлять физическую реалистичность без проверки.**

### M5 — улучшенная графика

Рендерер LWJGL/OpenGL, обновление текстур на GPU, освещение, визуальные эффекты. Изначально сохранить симуляцию на CPU.

### M6 — игровой процесс

Прогрессия, оборудование, опасности, управление водой, добыча с учётом материала, инвентарь и цели.

## Открытые вопросы проектирования

- Клетки мира размером с пиксель или более крупные блоки ландшафта плюс мелкие частицы? **Предварительный выбор:** одинаковые клетки для M1; пересмотреть после создания прототипов добычи и структурной механики.
- Как должны падать или разрушаться большие связанные массивы породы?
- Как приближённо моделировать объём и давление воды в разных масштабах?
- Какому масштабу соответствует одна клетка в будущей игре?
- Какой целевой производительности следует ожидать для активных клеток на целевом оборудовании?

## Критерий готовности изменений

Изменение считается готовым, когда оно компилируется, тесты проходят, поведение можно продемонстрировать, границы архитектуры сохранены, а README или эта спецификация обновлены при изменении поведения либо устройства проекта.
