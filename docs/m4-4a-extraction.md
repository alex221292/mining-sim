# M4.4a — stationary rock extraction

`ExtractionPlanner.prepare(world, connectivity, x, y, maxCells)` reads completed connectivity and produces `READY` with an immutable coordinate list, revision, component ID, normalized `FragmentDescriptor` and world origin. It rejects pending topology, non-stone, supported or oversized components. Planning does not mutate either owner. Only generic STONE maps to `SubstanceRegistry.STONE` (2500 kg/m³); GRAVEL and bedrock are not extracted. Direct bedrock-connected components are not eligible; topological support is not a mechanical stability verdict.

`ExtractionCommit.commit(plan, registry)` rejects stale revisions and active bond traversal, reconstructs and verifies the complete current component, geometry, placement, substance and mass, and preflights registry capacity, ID, overflow and the entire destination state. Expected failures return a status without changing either owner. World and registry are owned by one simulation thread; no other code may mutate or observe them concurrently or re-enter the transaction. This is not a cross-thread transaction or persistence transaction.

`World.replaceAllIfMatches` validates every coordinate, expected/replacement material and duplicate before any write; it checks bedrock protection and orders changes by y/x. No-op batches generate no event. For extraction, a `FragmentRegistry.Prepared` contains the preallocated immutable next registry state and a revision-protected reservation; world validates that every actual STONE→AIR change exactly matches the generic-stone fragment's geometry before writing. World applies the prevalidated cell writes, publishes the prepared registry state with allocation-free assignments, and only then calls `ChangeSink.changedBatch` once with an immutable list. Thus compliant callbacks see both complete owners. Registry changes cannot intervene between preflight and publication under the single-thread, non-reentrant contract. Sink callbacks must not throw or mutate the world, as before; VM failures and contract violations are not claimed recoverable. Ordinary `set` retains its existing per-cell callback.

`RockConnectivity.changedBatch` clears only incident broken-bond bits, updates changed-cell incarnation tokens, increments topology revision once and marks components pending. Distant broken bonds and their damage incarnations are preserved; `invalidated()` is not used. Recompute connectivity between component commits; old mechanical snapshots are stale after the revision change. The callback performs no flood-fill or solve.

`RockFragment` stores a monotonic registry ID, immutable descriptor, origin in world-cell coordinates, zero orientation and source component ID. World `(originX+localX, originY+localY)` is the original cell position; no transform jump occurs. One STONE cell is 2,500,000 mg, so `static stone before = static stone after + newly registered fragment mass`. Registry mass uses checked integers. Fragment ownership is separate from World; rendering overlays stationary tinted cells. There is no fragment motion, collision, debris, inventory, or persistence. The current renderer does not prevent subsequent painting or cellular material from occupying the same positions as stationary fragments; collision/occupancy integration is deferred and this representation is not yet physical. User-driven World.clear also does not clear fragment registry; reload the scene for a full reset.

In reference scenes, select a component with middle click and wait until `UNSUPPORTED` has appeared, then F5 explicitly extracts that selected component. This gate preserves diagnostics and avoids automatic extraction in normal worlds. One extraction makes connectivity pending; wait for a subsequent structural tick before selecting and extracting another. The original selected cell becomes AIR and HUD reports NO SELECTION after rebuild. F4 scene reload constructs a fresh registry and restarts IDs. Fragments render at original coordinates through `Camera2D`, but no graphical interaction was manually verified in this environment.

`gradlew.bat test build` covers batch rejection, single complete notification, unrelated broken-bond preservation, incarnation, stale/full plans, exact ownership/mass, deterministic IDs, preallocated reservation reuse, controller selection and reset. `gradlew.bat fragmentExtractionBenchmark`, Windows 11 Java 25, one exploratory run: 1/6/32/64 cells planning 25.525/0.335/0.767/0.544 ms, validation+commit 9.854/0.458/0.739/0.797 ms, connectivity rebuild 0.028/0.030/0.030/0.031 ms, snapshot 0.000040/0.000022/0.000024/0.000022 ms; 6-cell fixture is L-shaped. Sixteen isolated cells sequentially took 4.610 ms including rebuilds. The first measurement includes JIT/class loading; timings are exploratory and no full-world performance is claimed. M4.4b must address motion, collision/occupancy and persistence before fragments behave as physical bodies.
