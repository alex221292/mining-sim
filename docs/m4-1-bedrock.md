# M4.1 bedrock and mutation boundary

`World(width, height)` constructs a `LEGACY` world; the explicit `World(width, height, World.Mode.BEDROCK_ENABLED)` constructs a world whose entire bottom row is immutable BEDROCK (static ID 7). No ordinary `set` can create bedrock in either mode. The interactive sandbox uses the latter; legacy worlds retain their unrestricted bottom row. There is no migration API.

`set` checks bounds and null, then returns `CHANGED`, `NO_OP`, or `REJECTED`. Only actual changes mark activity and notify an optional synchronous `ChangeSink.changed(x,y,previousId,nextId)` in write order. Attaching a sink invokes `invalidated()` to require an initial rebuild; `clear()` invokes it once after the bulk operation, even for an already empty world. Consumers rebuild from the world on invalidation. There is no bounded queue or event retention: the single consumer must process every callback synchronously, must not throw or mutate the world, and must be attached before observing changes. The application owns the world on one thread. Clear preserves bedrock without clearing the bottom row; legacy clear removes all cells. Both retain the existing all-tiles activity invalidation. There is no separate reset operation.

MSIM v1 accepts IDs 0–6 only, loads as LEGACY, and retains the original encoding and CRC. Saving a BEDROCK_ENABLED world through either v1 API fails before writing bytes or touching the destination; the UI displays the I/O error. Legacy files with occupied bottom rows remain unchanged. No v2 or conversion exists, so new interactive worlds cannot currently be saved.

Exploratory `gradlew.bat benchmark`, Java 25.0.5, Windows 11, seed 12345, five batches after warmup: dense FULL_SCAN 1600×900 before mean/median/p95 19.268/19.219/20.386 ms, after 19.241/19.213/19.752 ms. At 400×300 active: 1.509/1.508/1.558 vs 1.749/1.748/1.865 ms. Empty and static 1600×900 increased from approximately 3.0 to 3.8 ms; these noisy single-run figures do not isolate mutation cost. No sink was attached. This exploratory benchmark is not a controlled microbenchmark; more runs and profiling are needed before attributing changes.
