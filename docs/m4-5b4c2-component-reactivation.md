# M4.5b.4c.2 — disconnected settled components

Removing cells can split one settled record into several orthogonally connected components. The support coordinator analyzes each affected component separately, using deterministic `(settledId, first row-major cell)` keys and the existing conservative vertical load/moment model. Only unsupported components transfer to rigid ownership; supported cells remain in World with their original settled owner and substance. New rigid bodies have separate connected descriptors, deterministic IDs and recorded source-settled mappings. Removed cells are an explicit edit, not conserved as remaining rock.

The component graph is read-only and resumable. Enumeration, neighbour checks, contacts, load propagation and result classification share `graphWorkPerTick`; a call reports its actual work. Terrain, topology or ownership revision changes invalidate unfinished work. While analysis is pending, the existing support gate prevents direct transitions; cellular simulation continues. A hard graph/group/cell limit refuses the operation without partial publication. Once analysis completes, the existing prepared-plan validation and `commitGroupReactivation` publish World, ownership, fragments, bodies and occupancy together. **Plan construction and the indivisible commit are separate from `graphWorkPerTick`** and may cost more than one graph work unit; commit is measured separately below.

Tests cover the erased five-cell base with two supported remnants and two unsupported upper rocks, one owner with independently supported/unsupported remnants, multiple bodies from one source, veto, callback state, exceptions, stale plans, deterministic replay and resettling. At `graphWorkPerTick=1`, the two-remnant fixture completes its coordinator analysis in 72 calls, with maximum recorded preparation work 1 per call, while cellular sand advances. The pre-existing 134/134/526 fixture remains covered. The conservative model may still reject physically stable configurations; no change was made to SAT, SWEPT, sleep, friction or the save format. GUI manual acceptance was not performed.

## Measurements

OpenJDK 25.0.5+8-LTS, OpenJDK 64-Bit Server VM, Windows; one JVM, two warmups, ten measured runs. `java -cp build/classes/java/main miningsim.structural.ComponentLifecycleBenchmark 10` uses a 20×20 partially erased component with `graphWorkPerTick=256`: analysis per tick, including the commit tick's analysis portion, mean/p95/max **0.051/0.129/0.143 ms** (20 samples); separate atomic commit **0.009/0.018/0.018 ms** (10); ticks to reactivation mean/p95/max **2/2/2** (10). Plan construction is excluded from both numbers. Timings include normal JVM/OS noise and are not FPS.

`java -cp build/classes/java/main miningsim.benchmark.HeadlessLifecycleBenchmark 10`: in the 64×64 134/134/526 fixture, whole ordinary tick **8.908/14.145/18.968 ms** (mean/p95/max, 3,470 samples); whole settling-transition tick **7.521/16.225/16.225 ms** (10); the settling commit phase alone **0.704/0.756/0.756 ms** (10). This benchmark covers initial settling, not a complete 134/134/526 reactivation cycle.
