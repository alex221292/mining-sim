# M4.5b.2 — group settling integration

This headless-only experiment prepares a bounded group placement and publishes World, fragment removal, rigid membership, occupancy and separate settled ownership inside one owner-thread batch. It is not wired into Swing and does not implement re-detachment or extraction of settled rock. The caller must observe every attempted coupled tick with `GroupSettlingEligibility`; all selected bodies must sleep for 120 consecutive successful observations, with bounded pose drift. Preparation checks source proximity within 0.05 cells, penetration, obstacles and group placement. The greedy assignment is incomplete and limits a group to three bodies and 2,048 cells. Its vertical, frictionless balance reaches BEDROCK but is not a bond-strength or impact-stability analysis. One cell is 0.1 m.

Veto sees old state, and the post-publication callback sees new state under the existing single-owner, non-reentrant, non-throwing callback contract. Failed preparation and stale plans do not publish. The source-support check conservatively requires a path through downward proximity contacts to BEDROCK; candidate placement is independently checked by the limited vertical balance. Search, contact and collision validation share a 2,000,000-unit budget, with bounded occupancy preparation separately. The API is not a general-purpose transaction system. `gradlew.bat test build` covers group publication, callbacks, veto, stale revisions and pose, occupancy preparation failure, deterministic replay and the 794-cell stack. No GUI verification was performed.

Exploratory sequential measurements on OpenJDK 25.0.5, Java VM defaults, no rendering. Single-cell cases: 400×40, 1/10/50 separate bodies, sequential single-body group commits; 120 quiet ticks are reacquired after each terrain/ownership change. Times include JIT and are not stable performance guarantees. Stack: 64×64, 134/134/526 cells, five fresh fixtures, 500 warmup ticks, 60 timed ticks before and after each commit.
