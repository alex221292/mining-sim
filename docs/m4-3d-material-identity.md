# M4.3d — material identity and resource contracts

These are headless value objects and pure plans in `miningsim.resource`; they are not integrated into simulation, saves, GUI, inventory gameplay, rigid bodies or crafting. `SubstanceId` is a stable string independent of registration order; `SubstanceProperties` holds name, integral density kg/m³, classification and an optional structural-property extension. Reference IDs are `stone`, `marble`, `granite`, `limestone`, `clay`; densities 2500, 2700, 2700, 2400 and 1800 kg/m³ are example values, not calibrated measurements. `MaterialForm` describes shape or processing, independently of identity. `MaterialSample` pairs identity and form; neither is allocated per world cell. This prototype does not yet provide an applicability catalogue for form/substance combinations.

Mass is an exact nonnegative `long` number of **milligrams** of solid substance; one 0.1 m cube is 0.001 m³, so one cell weighs `densityKgPerM3 × 1000` mg. The API accepts integral density only: fractional density requires an explicitly specified future conversion/rounding policy; it never silently rounds. Arithmetic uses exact operations and throws on overflow. Grit/sand/dust quantities are solid-equivalent mass, not bulk occupied volume. Porosity, compaction and packing are not modelled. Mechanical solver SI doubles remain separate.

`FragmentDescriptor` validates an immutable, nonempty, orthogonally connected, duplicate-free set of nonnegative local cells, sorted by y then x, and derives dimensions and mass from geometry and substance density. Coordinates remain in the original local frame after partition; dimensions describe the tight bounding box. Descriptors are not bodies and contain no position or rotation; a future body can own one and supply a transform. `partition` checks exact disjoint coverage and produces connected pieces. `FragmentationPlan.select` uses an explicit seed and original surface cells (orthogonal exposed edges); removed cells become same-substance grit, while the remaining connected components become descriptors. Empty remainder is valid. This is a pure proposal only: no World mutation, cells, physics or actual fragmentation.

`ItemType` has an explicit stable string ID, quantity kind, mass per unit and pickup flag. COUNT quantity is item count with explicit mg/item; MASS quantity is mg (one mg per unit). `ItemStack` adds substance/form and metadata to stacking identity. `InventorySnapshot` uses fixed optional slots; `InventoryInsertion.insert` returns a new snapshot and remainder, filling compatible stacks then empty slots in ascending order, limited by slots, per-ID quantity limit and total mg. Boulder form is never pickupable, regardless of weight. Example rules 24 slots, 25 kg = 25,000,000 mg, 64 pebbles/stack, 1000 mg grit/stack are configurable, not final balance. Zero input quantity is accepted; negative values and overflow are rejected. Rules do not yet describe equipment, volume, per-substance form validity or mixed-mass individual pieces.

`CraftingRecipe` is a declarative one-batch contract: ingredient identities/forms/quantities and output plus explicit per-substance constituent masses. It checks exact per-substance and total conservation, including binders. The composition map is an extension point, not a full recipe engine; a later inventory/persistence design must retain it for each composite item. Metadata currently identifies variants as an opaque string; composite ingredients and transformations into different substances require additional explicit contracts.

Examples:

1. Three connected marble cells have 8,100,000 mg. Partition two cells as marble rock pieces (5,400,000 mg) and plan one surface cell as marble grit (2,700,000 mg): the identity and total mass are preserved.
2. Granite pebbles and marble pebbles have different `MaterialSample`s and occupy separate stacks even when `ItemType` matches. Marble grit is separate again.
3. Two 1000 mg marble pebbles plus 500 mg clay yield one 2500 mg `CRAFTED_BLOCK` with composition `{marble: 2000 mg, clay: 500 mg}`. This is an illustrative recipe, not a mandatory game rule; it is distinguishable from monolithic marble.

The sole implemented legacy mapping is `Material.STONE` to generic stone / `SOLID_MASS`; legacy `GRAVEL` has **unknown substance** and is not reinterpreted. Other legacy IDs have no resource mapping. A future explicit compact world palette can map cell IDs to substance/form pairs with a versioned migration and lossless ownership rules. Existing byte arrays, IDs 0–7, simulation, structural scenes and MSIM v1 reader/writer remain unchanged. No new world materials or palette persistence are implemented.
